- **2026-10-08 — D-40 — Page actions over WebMCP (AI-21), built now as v1.1.** The user brought a proposal for actions the agent can pick from: each page, or part of a page, registers what can be done right here (site-wide, per page, per element), the agent chooses only from that list, missing details are asked for with UI generated from the params, a risk level decides auto / confirm / human, the action runs in the visitor's browser, Done with Undo. Decided: (1) the contract is WebMCP (Chrome's imperative `document.modelContext` tools; declarative `<form toolname>`), not a Jun-only API, so one investment by the host serves Chrome's agent and ours and we inherit the docs; the loader polyfills `document.modelContext` where absent and defers to native where present; Jun extras (`pages`, `key`, `element`, `undo`, `context`, `available`) live only in our registry via `JunDesk.registerAction`, a superset. (2) First version: code-registered actions in full; declarative forms only where Chrome supports them natively; our own form filling deferred (D-39's line). (3) AI-06 folds in as the `confirm` risk level (the default; `consequentialHint` maps to it) and W-09 as the param UI generated from a tool's input schema. (4) Server shape: a chosen browser action ends the AI turn, the widget runs it and sends the result, which the next turn reads; the DO never awaits the browser. (5) Built before launch, while M8 waits on the public repo and video; sites that register nothing are unaffected. AI-22 (GUI fallback, from reviewing Alibaba's Page Agent) stays `later` below it. Spec churn is tracked in CLAUDE.md "WebMCP conventions".

- **2026-10-10 — D-42 — The model's decisions are tool calls, not control lines in its text.** The reply used to carry `HANDOFF: <reason>` (first line), `ESCALATE: <summary>` (last line) and `FOLLOWUPS: q | q`, found by parsing the text and held back from the stream while a line might become one. Workers AI's Mistral put `HANDOFF:` mid-reply ("I'm sorry, I can't do that for you. HANDOFF: …"): the visitor saw the internal line and nothing was handed off. The user asked for the proper fix rather than searching the text harder. Decided: `handoff({ reason })` and `flag_problem({ summary })` (offered only with debug context), read from the response's tool calls (`runAgent`, `replyOutcome` in `worker/ai/agent.ts`); the outcome shape is unchanged, so the Conversation object, evals and widget are too. Handoff has no `execute` (the call ends the turn, like a page action). Flagging runs, because Mistral doesn't reliably write text and call a tool in one response: the model flags first and explains in the next step, and a step that already explained ends the loop (otherwise Mistral wrote its whole reply again). Words written before a handoff stay as the AI's message, then the notice. Nothing is held back from the stream any more. `tools/<name>.yaml` can't take the built-in names. E2E on ChatGPT and Workers AI: chat, AI, debug, agent and page actions pass; no reply contains a control string. Follow-up questions were never produced in production with the old line (0 of 303 AI replies), and a `suggest_followups` tool wasn't called either (0 of 31 e2e replies, both providers); the user chose to have them written by a separate fast job instead (`followups`, AI-16's list): after an answer that used the knowledge is saved, one small call writes up to 3 questions from the question, the answer and its sources, and they're added to the message in place, a moment after the answer.
- **2026-10-10 — D-43 — Widgets (W-09) in v1, in OpenAI's ChatKit widget format, with our own template engine and renderer.** The user looked at Chatbase's new Widgets (a builder for cards the bot shows: AI builder, JSX-like code, Zod schema, functions, states; observed in their dashboard 2026-10-10) and ChatKit Studio (widgets.chatkit.studio), and asked for widgets now rather than in v2. The card rides on the tool's finished step (live) and is saved as `meta.widgets`. Buttons, a Form's submit and Card confirm/cancel send a visitor message (the button's label) with `meta.widgetAction` (card, action type, payload, the card's own field values); the Conversation object checks the action against the card it showed (forged or repeated presses are refused) and marks the card used; the AI's next turn reads it as one line (`widgetActionLine`). Not built: ChatKit's client-handled actions, `onChangeAction`, `Transition` animations; actions don't call tools directly (the AI decides).
