# Jun Desk

An open-source, AI-first customer support desk for B2B SaaS, deployable to your own Cloudflare account in one click: an embeddable website widget, live visitor tracking, an AI agent that answers and takes actions, and a real-time inbox for human agents. Think Intercom/Fin, Chatbase, Crisp — rebuilt for 2026.

## Current phase: v1 launch prep (M0–M7 deployed; M8: wizard, upgrade check and S-08 issues built). No production launch for now (D-81); ChatGPT sign-in stays always on for the owner's desk (D-27), re-gating it is backlog (checklist in `docs/build-plan.md` M8)

Plan: `docs/build-plan.md`. Build milestone by milestone; keep the Deploy button working at every step.

## Code

npm workspaces. `packages/` TypeScript runs directly on Node ≥22.18 (type stripping, no build step); `worker/` and `web/` are bundled by Vite:
- Only erasable TS syntax (no enums, namespaces or constructor parameter properties); relative imports use `.ts` extensions.
- `packages/llm` uses web-standard APIs only (fetch, crypto.subtle, web streams) so it runs on Node and Cloudflare Workers. Node-only code goes in `packages/cli`.
- `packages/` has zero runtime dependencies; the app uses Hono, React (the widget frame builds on Preact via `preact/compat`, D-41: `widget` environment in `vite.config.ts`; dev serves it on React, so check widget changes on `vite preview` too), SimpleWebAuthn, the AI SDK (`ai`, `workers-ai-provider`, `@ai-sdk/openai`, `zod` peer) `yaml` (D-22) and `lucide` (ISC; widget card icons beyond our own, lazy-loaded, D-51); the dashboard uses Tailwind v4 + shadcn/ui (`@base-ui/react`, `cn`, `class-variance-authority`, Hugeicons (`@hugeicons/react`, `@hugeicons/core-free-icons`, mapped in `web/components/icons.tsx`; D-35); D-30); `@shadcn/react` (MIT, no deps: the behaviour behind shadcn's Message Scroller, `web/components/ui/message-scroller.tsx`, written by hand from the registry because the CLI wanted to overwrite our `button.tsx`; used by the widget editor's AI chat, rows with `content-visibility: visible` since its 10rem estimate made new turns jump); the Dashboard's conversations chart uses Dither Kit (vendored shadcn registry code in `web/components/dither-kit/`, its `cn` pointed at ours; deps `motion`, `d3-scale`, `d3-shape`; lazy-loaded from `web/reports/DayChart.tsx` and `web/reports/charts.tsx` (topics donut + radar, team bars); seven files carry `@ts-nocheck` because they predate our `noUncheckedIndexedAccess`; its CLI can't spawn `npx` on Windows, so run the `npx shadcn@latest add https://tripwire.sh/r/<name>.json` it delegates to, then move the files from `components/` into `web/components/`); the Visitors globe uses `maplibre-gl` (lazy-loaded; one static map file `public/geo/world.v1.json` built from Natural Earth by `scripts/globe-data.ts`, labels drawn with Outfit via `font-faces`: no tiles, glyph server or map service). Add dependencies only with a clear reason.

WebMCP conventions (page actions, AI-21, D-40): the contract for actions a host page exposes to the agent is WebMCP, not a Jun-only API. Imperative: `document.modelContext.registerTool({ name, description, inputSchema, execute, annotations })`, `getTools()`, `executeTool()`, `toolchange`, unregister via `AbortSignal`; declarative: `<form toolname tooldescription>` with `toolparamdescription` / `toolautosubmit`, `toolactivated` / `toolcancel` events. The loader polyfills both where the browser lacks them (lazy chunk, only installed when `document.modelContext` is absent) and defers to native where present; Jun extras (`pages`, `key`, `element`, `undo`, `context`, `available`) live only in our registry via `JunDesk.registerAction` (a superset). The install snippet is `defer` in `<head>`, before the site's scripts: sites feature-detect `document.modelContext` once on mount (limoni.io does), and an `async` loader lost that race, so no tools were registered. `consequentialHint` maps to our `confirm` level, the default. **The spec is a W3C draft in a Chrome origin trial and moves every few releases** (as of 2026-10-08: moved from `navigator` to `document`; Chrome 153 unregistration no longer cancels in-flight runs; 155 deprecated JSON-string inputs; 156 added the `debugging` annotation and dropped `window.ontool*`). Before touching the polyfill, loader actions or docs, re-read https://developer.chrome.com/docs/ai/webmcp/imperative-api and https://developer.chrome.com/docs/ai/webmcp/declarative-api and note the date checked here. WebMCP covers only the page side; carrying the tool list to the model, choosing, the risk gate, audit and server actions are ours.

Visitor conventions (M6, D-23): identity only ever comes from a verified JWT (never from page JavaScript); identified contacts never merge with each other; visitor sockets on the hub receive only `LiveServerEvent`s (invites, identify results), never inbox events (`#broadcast` goes to the `agent` tag). Consent mode means no storage and no live socket before consent. Check the served loader size after loader changes (`gzip -c dist/client/widget.js | wc -c` after `npm run build`).

Notification conventions (I-14): the VAPID private key is generated on first use and kept only in the workspace hub DO's storage (`push:vapid`); the API returns the public key, devices without their p256dh/auth keys, and endpoints only as hashes. Recipients come from `notificationRecipients` (members only, never the actor, each person's toggles): unassigned "needs a person" → everyone opted in; round robin or a teammate's assignment → the assignee; visitor reply → the assignee; mention → the mentioned. Push text is the visitor's latest public message; internal note text only ever goes in a mention, to members. A focused desk tab (reported over the hub socket) means no push for that person; a hidden tab shows the same event as a system notification with the same tag and id, so a push of it replaces it silently. 404/410 from a push service deletes the subscription. Check `public/sw.js` stays small and never adds a fetch handler.

P1 conventions: never capture request/response bodies, storage, typed values or page text (rage clicks keep only tag, id, aria-label, name, role and a ≤ 40-char button/link label; `stuck` only the page path); mask in the browser *and* on the server; debug context only reaches agents (`/api/conversations/:id/context`) and the AI prompt, never other visitors. The model's decisions are tool calls, never lines typed in the text (D-42): `handoff({ reason })`, `flag_problem({ summary })` (only with debug context; P1 escalation), plus `jun_done` in page-action chains. `handoff` has no `execute` (the call ends the turn); `flag_problem` runs, so the model can flag first and explain next (Mistral doesn't write text and call a tool in one response), and a step that already explained ends the loop; `runAgent` reads the calls and `replyOutcome` (`worker/ai/agent.ts`) combines them with the text, so every streamed word is the visitor's and nothing is held back. Words written before a `handoff` stay as the AI's message, then the handoff notice. `tools/<name>.yaml` can't take those names. Follow-up questions are not asked of the reply at all (models never wrote them): a separate job writes them.

Realtime conventions: clients ping every 30 s (auto-answered, works while hibernated); the hub treats a socket with no ping for 75 s as gone (`#alive`: hidden from the visitor list, presence and auto-assignment, closed by a 1-minute sweep alarm), so tabs closed without a close frame or connections cut by a deploy don't linger; the visitor list shows one row per session. The Worker authenticates every socket upgrade (agent cookie, or visitor token as the 2nd WebSocket subprotocol) and forwards to the DO with `x-jun-*` headers; DOs trust those headers. Messages get `seq` from the Conversation DO and are idempotent per `clientMsgId`. D1 stays the source of truth.

Worker conventions: throw `HttpError` for expected failures (rendered as `{ error: { code, message } }`); non-GET API requests must be JSON (CSRF guard in `worker/index.ts`); IDs are prefixed random strings (`newId("usr")`), timestamps are epoch ms; secrets/tokens are stored only as SHA-256 hashes.

**Sign in with ChatGPT is always available for now (D-27), on the owner's desk before launch.** Locally it returns to the dev server on 127.0.0.1; on the deployed desk it ends on a 127.0.0.1 page whose address is pasted back into Settings. Fresh installs still default to Workers AI until an admin signs in. Re-gating is backlog (D-81, no production launch for now); if the desk is ever launched for others it must be re-gated (local dev or an explicit opt-in) and the default must stay Workers AI or an API key, since OpenAI's terms cover plan usage for your own use, not serving the public. Use only OpenAI's documented flow, never the Codex `backend-api` workaround.

## How we work (token use)

- Hand self-contained, multi-step work to a subagent (commit/test/deploy runs, the e2e suites, broad code searches, inspecting and measuring a reference page) and keep only its summary in the main conversation.
- Give the subagent everything it needs in the prompt (goal, files, constraints, what to report back): it doesn't see the conversation.
- Use the direct tools for quick, targeted reads and edits where the file is already known; a subagent costs more than it saves there.

## How we work on the docs

- **Features** use stable IDs (`W-01`, `AI-03`, …). Never renumber; retire with status `cut` instead of deleting.
- **Status values:** `proposed` → `agreed` → (later `building`, `shipped`), or `cut`. Only the user moves a feature to `agreed` or `cut` — Claude may *propose* changes and record them as `proposed`.

## Decided (see `docs/decisions.md` log)

- **Target customer: B2B SaaS.** Prioritise Slack Connect, debug context, issue-tracker links, account-level context.
- **Open source, one-click "Deploy to Cloudflare".** This is a hard constraint on every technical choice:
  - Everything must run on Cloudflare primitives the deploy button can auto-provision: Workers, Durable Objects, D1, Vectorize, R2, KV, Queues, Workers AI.
  - **No external services required** for a working install: no Postgres, Redis, Clerk/Auth0, or paid SaaS. Optional integrations are fine.
  - Workers only, not Pages; the deployable app must be self-contained in its directory.
- **Business model: open source + paid hosted cloud (cloud ships in v2).** Server/dashboard AGPL-3.0; widget, SDKs and agent-config format MIT; CLA required for contributions. Data model is multi-workspace from day one (the cloud is multi-tenant), even though self-hosted v1 shows one workspace.
- **Login: passkeys (D-17)**, owner created with `SETUP_TOKEN`, agents via invite links. No email or OAuth service required.
- **Data and layout:** D1 is the source of truth; each conversation's Durable Object holds live state and writes through to D1. One `conversation` table with a `chat`/`ticket` type. The Worker lives at the repo root; `packages/` builds into its assets.
- **Stack: Cloudflare.** Workers serve the API, dashboard and widget assets. Durable Objects handle realtime, presence and the per-conversation agent (Agents SDK). D1 holds durable records, Vectorize the KB, R2 files.
- **Positioning — three pillars** (`docs/research/05-differentiation.md`): **P1 support that sees the bug** (lead: the widget captures errors and failed requests, the AI diagnoses, files Linear/GitHub issues), **P2 your desk, your Cloudflare**, **P3 support agent as code** (config in git, evals). v1 must demo all three.
- **Slack is secondary, not a core feature or pillar.** The core is the widget, AI agent, debug context and inbox. v1 includes only team replies from Slack (handed-off chats); customer Slack Connect channels are v1.1; don't let Slack drive architecture or priorities.
